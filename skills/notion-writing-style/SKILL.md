# Notion 문서 서식

새로 작성하거나 수정하는 본문에 다음 규칙을 적용한다.

설명형 가이드를 새로 쓰거나 전체 전개를 다듬을 때는 [전개와 말투 참고](references/editorial-style.md)를 먼저 읽는다. 사용자가 고른 참고 글에서 정리한 편집 원칙이다.

- **설명체 말투** — 독자에게 배경과 판단을 설명하는 문단은 “~습니다”를 중심으로 쓴다. “~죠”, “~인데요”는 문맥에 맞춰 가끔 쓴다. 정의·라벨은 명사형으로 정리하고 실제 발언과 코드의 표기는 보존한다.

- **제목** — 본문 제목은 1단계와 2단계를 사용한다. 1단계 제목은 블록 배경을 회색(`gray_bg`)으로 설정하고, 제목 텍스트 맨 앞에 일반 공백을 정확히 한 칸 둔다.
- **제목 종결** — 페이지 제목과 본문 소제목은 명사 또는 ‘-임’, ‘-함’으로 끝낸다. 자연스러운 명사를 우선한다(예: 주문별 결제액 검증). 독자에게 직접 묻는 제목은 물음표로 끝나는 문장도 쓴다(예: 결제액이 왜 두 배가 됐을까?).
- **간격** — 1단계 제목 바로 앞에 내용이 있으면 빈 문단을 하나 넣는다. 문서 맨 앞이거나 바로 앞에 빈 문단이 있으면 추가하지 않는다. 1단계 제목 아래의 장식용 구분선은 생략한다.
- **문서의 역할** — 첫 독자가 읽은 뒤 내릴 판단이나 수행할 작업을 한 가지로 잡는다. 본문은 판단에 필요한 근거와 사례 순서로 쓰고, 분량이 큰 재현 절차는 하위 실습에 둔다. 각 페이지에서 같은 해설을 두 번 시작하지 않는다.
- **사례의 흐름** — 독자가 실제로 만날 질문에서 시작해 같은 사례의 입력·문제·판단·결과를 따라간다. 다른 사례로 넘어갈 때는 앞 사례가 남긴 질문과 새 사례가 답할 질문을 연결한다. 확인된 현장 경험, 공개 데이터 실측, 가상의 후속 요청은 문맥에서 구분한다. 장점은 “도움이 된다”로 요약하기보다 어떤 수정이나 검사가 쉬워지는지 보여 준다.
- **실습 편집** — 준비물과 시작 위치를 먼저 쓰고, 단계마다 실행할 명령 바로 아래에 독자가 확인할 기대값을 둔다. 의도한 실패는 테스트 이름·실패 조건·다음 행동을 명시한다. 표와 그림은 그 결과를 해석하는 곳에, 참고 파일 목록은 필요한 사람이 펼칠 곳에 둔다.
- **명사형과 문장형** — 이름을 붙이는 자리(제목·단계명·라벨·표의 짧은 값)는 명사구로 쓴다. 짧은 용어 정의는 “용어 · 정의”처럼 나란히 두고, 같은 목록의 항목은 형태를 맞춘다. 행동을 안내하거나 이유·사례·관찰 결과를 전할 때는 목록 안에서도 주어와 서술어가 맞는 문장으로 쓴다. 예: 단계명 “실패 재현”, 결과 “원천과 금액이 다른 주문 9,802건이 반환됐다.” 라벨과 설명이 한 줄에서 부딪히면 문단을 나눈다. 최종 검토 때 서술어만 뺀 본문, “테스트 2개 통과다”처럼 항목을 문장에 끼워 넣은 표현을 고친다.
- **줄바꿈** — 한 단락은 한 가지 생각, 보통 1~2문장으로 쓴다. 질문에서 답으로, 설명에서 예시·수치·판단으로 바뀌면 새 문단으로 나눈다. 한 블록 안의 긴 안내도 조건과 행동 사이에 줄바꿈을 넣는다.
- **목록** — 용어 둘 이상을 같은 형식으로 연달아 정의할 때는 한 용어당 한 bullet로 묶고 용어명은 인라인 코드로 쓴다. 조건·선택지·이점·준비물·파일처럼 독자가 골라 읽거나 비교할 항목이 나오면 bullet 목록을 적극 쓴다. 각 항목은 같은 관점으로 시작하고 한 가지 뜻만 담는다. 순서가 중요한 절차는 번호 목록, 이유와 맥락은 짧은 문단으로 잇는다.
- **인용** — 독자가 잠시 멈춰 읽을 고객 질문·요구사항·실제 발언은 가끔 네이티브 인용 블록(`>`)으로 분리한다. 실제 발언은 원문과 출처를 확인하고, 작성한 예시는 인용 바로 앞에 예시임을 밝힌다.
- **강조** — 강조할 단어 하나, 숫자 하나, 식별자는 인라인 코드로, 여러 단어가 한 뜻을 이루는 구절은 밑줄로 표시한다. 조사·마침표는 강조 밖에 둔다. 문장 전체에 장식을 씌우기보다 강조할 핵심만 고른다. 기울임꼴은 쓰지 않는다.
- **장표 배치** — 긴 기술 문서는 주요 질문이 바뀌는 지점마다 설명 곁에 장표를 자주 배치한다. 도입 외에도 범위·관계·변경 전후·검증 결과·선택 조건을 독자가 머릿속으로 재구성해야 하는 구간을 훑는다. 그림마다 새 질문에 답하게 하고 그림이 설명하는 문장은 줄인다.
- **장표 형식** — 문서 안에서는 `draw-diagram`의 그림 전용 PNG를 우선한다. 표 제목·단위·라벨은 그림에 두고 페이지 제목이나 본문 결론을 이미지 위아래에 반복하지 않는다. 사용자가 편집 가능한 Mermaid를 요청하면 네이티브 Mermaid 블록을 쓴다. 정확한 값 조회는 표, 실행 명령은 코드 블록으로 둔다.
- **삽화 너비** — 데이터의 양과 라벨 길이로 PNG 크기와 페이지 표시 폭을 각각 정한다. 짧은 비교는 작은 그림으로 설명 옆에 두고, 복잡한 표나 긴 흐름은 글자를 읽을 수 있을 만큼 넓힌다. 전체 너비 페이지에서도 작은 그림을 양끝까지 늘이지 않는다. 필요하면 네이티브 열에 그림과 관련 문단을 나란히 두고 저장된 열 비율을 확인한다.
- **표 너비** — 설명이 길거나 열이 많은 표가 있는 문서는 전체 너비를 켜고 표도 페이지 폭에 맞춘다. 항목명·숫자 열은 좁게, 설명·판단 기준 열은 넓게 지정한다. 셀 하나가 문단이 되면 절차나 예외를 본문으로 옮긴다.
- **사례 출처** — 사내 프로젝트가 처음 나올 때 고객 과제와 사례가 쓰인 이유를 한 문장으로 소개한다. 수치나 경험을 전하는 바로 다음 줄에 해당 Slack 원글·답글이나 Notion 페이지를 네이티브 멘션으로 붙인다.
- **멘션** — Slack 메시지·스레드·채널, 다른 Notion 페이지·DB·사람 등은 네이티브 멘션으로 연결한다. 작성자·채널·발췌문이 붙는 긴 출처 멘션은 문장을 완결한 뒤 별도 줄에 둔다. 멘션 뒤에 조사를 이어 쓰거나 같은 하위 페이지를 두 번 나열하지 않는다. Slack 메시지는 실제 permalink를 Notion 편집기에 붙이고 ‘붙여넣기 형식 → 멘션’을 선택한다. 화면에서 작성자·메시지 발췌·Slack 아이콘·채널명이 표시되고 같은 원문을 여는지 확인한다. 커넥터의 slackMessage:// 주소만으로는 멘션 여부를 판정할 수 없다. 외부 공식 문서 등 멘션을 지원하지 않는 대상은 설명형 링크를 쓴다.
- **전체 퇴고** — 제목만 읽어도 질문의 순서가 이어지는지, 첫 사례가 설명되기 전에 재사용을 이야기하지 않는지, 단락 끝에 앞의 말을 되풀이한 결론이 없는지 확인한다. 실습은 제공 파일에서 명령 순서·경로·기대값을 대조한다.
- **게시 후 확인** — 긴 단락, 기울임, 그림 배치, 표 너비, 클릭 대상과 중복 링크를 확인한다. 일반 링크와 실제 멘션을 구별하고 화면에서 확인할 수 있으면 줄바꿈·잘림과 Slack 아이콘도 확인한다.
